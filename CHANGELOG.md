## Changelog

This page lists the changes to this manual that affect an integration: a field name, type, length, required flag or allowed value, an endpoint or HTTP method, an error code, how Sandbox and Live behave, or a rule your Merchant Server must follow. Changes to layout, wording, diagrams and links are not listed.

If you built your integration from an earlier version of this manual, check the areas you use. Each entry states what is true now in bold, then what the manual said before, then what to check, with a link to the section that explains it.

<br>

### September 2026

Between 18 and 24 September 2026, every page of this manual was checked against how the API behaves and corrected. Before that, the manual had last changed in March 2024.

#### Authentication and keys

- **Checkout needs a Client Authentication client key.** Not documented before. With a Server Authentication key, the Hosted Payment Page rejects the customer with `P025`, and `tosspayBill` fails at Create checkout with `U147`. Check your Checkout key type. Key-in Payment and Recurring Payment accept either type. See [Client Key Type](./info/nicepay-info-key.md#client-key-type).

#### Checkout

- **`apprStatus`, `updateDate`, `zidxHigher`, `disableScroll` and `disableEdgeChk` were removed from the manual.** The Create checkout response does not return them. Read the session status from `status`, and drop any code that depends on the other four. See [Create Hosted Payment Page Response Example Code](./api/nicepay-api-payment-window-url.md#create-hosted-payment-page-response-example-code).
- **Create checkout has no `bid` request field.** The manual listed one. `bid` is the path parameter of `POST /v1/subscribe/{bid}/payments`. Stop sending `bid` to Checkout, and charge a token through Recurring Payment. See [Hosted Payment Page Request Parameter](./api/nicepay-api-payment-window-url.md#hosted-payment-page-request-parameter).
- **The callback field is `buyerTel`, with a lowercase `b`.** The manual said `BuyerTel`. Read `buyerTel` from the `returnUrl` callback. See [Payment Authorization Response Parameter](./api/nicepay-api-payment-window-url.md#payment-authorization-response-parameter).
- **Only `isExpire` shows whether a session expired, and `expireDate` is when its validity ends.** The manual listed an `expiredAt` field, which the API does not return, and described `expireDate` as `true : Expired`. Test `isExpire`, and parse `expireDate` as shown in [Dates in responses](./info/nicepay-info-general.md#dates-in-responses). See [Hosted Payment Page Response Parameter](./api/nicepay-api-payment-window-url.md#hosted-payment-page-response-parameter).
- **`vbankExpDate` is a String holding a KST date and time, such as `2023-03-25T23:59`.** The manual said an Int in `yyyyMMdd` form. Send the date-time string: `yyyyMMdd` fails with `U330`, and a date alone leaves the closing time unconfirmed. See [Dates in requests](./info/nicepay-info-general.md#dates-in-requests).
- **`isDigital` is a Boolean: `false` for content, `true` for physical goods.** The manual said an Int, `0` or `1`. Send a JSON boolean when `method` is `cellphone`. See [Phone bill Option](./api/nicepay-api-payment-window-url.md#phone-bill-option).
- **The callback's `canPartCancel` is a Boolean.** The manual said a String with no listed values. Parse it as `true` or `false`. See [Payment Authorization Response Parameter](./api/nicepay-api-payment-window-url.md#payment-authorization-response-parameter).
- **`cardType` is `credit` or `check` (debit card), up to 6 bytes.** The manual listed `1` (individual), `2` (corporation) and `3` (overseas) in 1 byte. Map the two text values in your callback handler and test fixtures. See [Payment Authorization Response Parameter](./api/nicepay-api-payment-window-url.md#payment-authorization-response-parameter).
- **Expire checkout session is `POST /v1/checkout/{sessionId}/expire`.** The Checkout page said `GET`, while the URI list said `POST`. Call the expire endpoint with `POST`. See [Expire Checkout session Request Parameter](./api/nicepay-api-payment-window-url.md#expire-checkout-session-request-parameter).
- **The payment result reaches your `returnUrl` as a form `POST`, not as JSON.** The manual showed `GET /v1/checkout/{sessionId}` and JSON bodies with nested `card` and `vbank` objects. Parse flat, URL-decoded form fields in Sandbox and Live, and allow `couponAmt` to be empty or the text `null`. See [Payment Authorization](./api/nicepay-api-payment-window-url.md#payment-authorization).
- **Redirect the customer to the `url` of the Create checkout response exactly as returned.** The manual showed Hosted Payment Page addresses built from `sessionId` alone. Never assemble this address yourself. See [Base URL information for Sandbox and Live](./info/nicepay-info-sandbox.md#base-url-information-for-sandbox-and-live).
- **`sessionId` can be up to 256 bytes.** The manual said 64 bytes. Size your `sessionId` columns and validation for 256 bytes, including values from Transaction Status Inquiry and webhooks. See [Hosted Payment Page Request Parameter](./api/nicepay-api-payment-window-url.md#hosted-payment-page-request-parameter).
- **`returnUrl` accepts up to 2500 bytes.** The manual said 500 bytes. Remove any 500-byte cap from your validation. See [Hosted Payment Page Request Parameter](./api/nicepay-api-payment-window-url.md#hosted-payment-page-request-parameter).
- **`goodsName` accepts up to 100 bytes, but `tosspayBill` and `kakaoBill` cut it at 40 bytes.** The manual said 40 bytes for every method. Keep `goodsName` within 40 bytes for those two methods, because the rest is dropped with no error. See [Hosted Payment Page Request Parameter](./api/nicepay-api-payment-window-url.md#hosted-payment-page-request-parameter).
- **The callback's `bankCode`, `bankName`, `channel` and virtual account fields can be empty.** The manual marked `bankCode`, `bankName` and `channel` as required. Read the virtual account from the `vbank` object, and the bank from the `bank` object, of Transaction Status Inquiry. See [Payment Authorization Response Parameter](./api/nicepay-api-payment-window-url.md#payment-authorization-response-parameter).
- **Checkout session `status` is `ready`, `pending`, `paid`, `failed`, `closed`, `cancelled` or `partialCancelled`.** The manual listed `canceled`, `partialCanceled` and `expired`, and used `ready` for an issued virtual account. Handle `pending` and `closed`. Outside Sandbox `fakeAuth` sessions, a virtual account session turns `paid` at issuance, not at deposit. See [Retrieve Checkout session Response Parameter](./api/nicepay-api-payment-window-url.md#retrieve-checkout-session-response-parameter).
- **The callback `status` is `paid`, `ready`, `failed` or `closed`.** The manual also listed `canceled`, `partialCanceled` and `expired`. Handle `closed`, which means the customer left the Hosted Payment Page, and treat `failed`, including `U504`, as not paid. See [Payment Authorization Response Parameter](./api/nicepay-api-payment-window-url.md#payment-authorization-response-parameter).
- **The callback `payMethod` can also be `bank`, `cellphone` or `tosspay`.** The manual listed only `card`, `vbank`, `naverpay`, `kakaopay`, `payco`, `ssgpay` and `samsungpay`. Map the three added values in your callback handler. See [Payment Authorization Response Parameter](./api/nicepay-api-payment-window-url.md#payment-authorization-response-parameter).
- **The customer's browser posts the result to `returnUrl`, and NicePay never retries it.** The manual said NicePay delivers the result. Do not limit `returnUrl` to NicePay IP addresses, return your order result page, and use the webhook or Transaction Status Inquiry when no callback arrives. See [Payment Authorization](./api/nicepay-api-payment-window-url.md#payment-authorization).
- **Checkout `expireDate` accepts only UTC with `Z` or an offset without a colon.** The manual said any ISO 8601 value. `+09:00` or no offset fails with `U322`. The default, 1 day or 1 hour by merchant account, appears in the response. See [Dates in requests](./info/nicepay-info-general.md#dates-in-requests).
- **In Live, `vbankValidHours` overrides `vbankExpDate`, and no default is confirmed.** The manual said 7 days by default, counted from issuance. Send one of the two fields. `vbankValidHours` counts from when the customer opens the Hosted Payment Page, and 0 or less fails with `U339`. See [Virtual account Option](./api/nicepay-api-payment-window-url.md#virtual-account-option).
- **Installments need an `amount` of 50,000 or more, whatever the `currency`.** The manual said more than KRW 50,000. Treat exactly 50,000 as allowed, and compare the raw `amount` number for `USD` and `CNY` too. See [Cards & Wallets](./api/nicepay-api-payment-window-url.md#cards--wallets).
- **`returnCharSet` sets only the charset of the page that posts the `returnUrl` callback.** The manual did not state its effect. Keep `utf-8`: the Create checkout response is always UTF-8, EUC-KR cannot carry many non-Korean characters, and an unlisted value fails with `U132`. See [Hosted Payment Page Request Parameter](./api/nicepay-api-payment-window-url.md#hosted-payment-page-request-parameter).
- **Only `fakeAuth: true` skips card company authentication in Sandbox, and Live does not reject the field.** The manual showed `fakeAuth` only in examples and said Sandbox always skips it. Never send `fakeAuth` in Live, where the returned `url` opens the dummy page. See [Hosted Payment Page Request Parameter](./api/nicepay-api-payment-window-url.md#hosted-payment-page-request-parameter).
- **The browser table no longer lists Windows XP or Internet Explorer on Windows 11, and the Hosted Payment Page stops Internet Explorer 8 and earlier.** The manual listed both as supported. Do not rely on Safari on iOS, Chrome on Android or in-app WebViews, which are unconfirmed. See [Browser support(PC)](./info/nicepay-info-general.md#browser-supportpc).
- **Your Merchant Server creates `sessionId` and `orderId`, and neither can ever be reused.** The Sandbox guide said NicePay generates `sessionId`. Never reuse either value, even from an expired or failed session: a used `orderId` fails with `U112`, and a used `sessionId` with `U324`. See [Create a checkout](./info/nicepay-info-sandbox.md#create-a-checkout).
- **Confirm an order only after the full callback checks.** The manual only said to check the amount with `signature`. Find the order by `orderId`, require `resultCode` `0000`, verify `signature` (lowercase hex), compare `amount`, and confirm with `GET /v1/payments/{tid}`, since `signature` skips `orderId` and `status`. See [Verifying the payment result](./api/nicepay-api-payment-window-url.md#verifying-the-payment-result).
- **A second callback for a paid session can report `P045`, `P047` or `P049`, and the webhook can come first.** Not documented before. Keep an already paid order paid, and apply the first of the webhook and the callback that passes the checks, once. See [Verifying the payment result](./api/nicepay-api-payment-window-url.md#verifying-the-payment-result).
- **For `vbank`, the callback arrives when the account is issued, with `status` `ready`.** The manual listed `ready` (virtual account number) but did not say the customer has not paid. Do not ship yet. Register a webhook for `vbank` or `all` for the deposit, or poll Transaction Status Inquiry, and read the account number from its `vbank` object. See [Virtual account Option](./api/nicepay-api-payment-window-url.md#virtual-account-option).
- **Checkout `method` also accepts `naverpayPoint`, `naverCardBill`, `naverPointBill`, `kakaoBill`, `tosspay`, `tosspayCard`, `tosspayMoney` and `tosspayBill`.** Not documented before. Use them to offer Naver Pay points, Toss Pay, or easy-pay recurring enrollment through Checkout. See [Hosted Payment Page Request Parameter](./api/nicepay-api-payment-window-url.md#hosted-payment-page-request-parameter).

#### Recurring Payment

- **`messageSource` was removed from the Delete Token response.** The API does not return it. Remove any code that reads it. See [Delete Token(bid) Response Parameter](./api/nicepay-api-billing.md#delete-tokenbid-response-parameter).
- **`signData` in the Create Token request is a String.** The manual typed it Int. Send it as the hex string hex(sha256(`orderId` + `ediDate` + SecretKey)). See [Create Token(bid) Request Parameter](./api/nicepay-api-billing.md#create-tokenbid-request-parameter).
- **`idNo` and `cardPw` in the Create Token `encData` are required by authentication type.** The manual marked both optional. Include `idNo` with authentication type `10` or `11` and `cardPw` with type `03` or `11`, and handle `U317` (check against your type failed) and `F101` (`encData` cannot be decrypted). See [encData Field Details](./api/nicepay-api-billing.md#encdata-field-details).
- **`cardQuota` and `useShopInterest` must be left out when charging a `tosspayBill` token.** The manual marked both always required. Keep sending them for other tokens, and drop them when `method` is `tosspayBill`, or the charge fails with `U143`. See [Recurring Payment - Authorization Request Parameter](./api/nicepay-api-billing.md#recurring-payment---authorization-request-parameter).
- **`signature`, `card`, `issuedCashReceipt` and `messageSource` are present in every successful charge response.** The manual marked them optional. Verify `signature` on every charge response whose `resultCode` is `0000`. See [Recurring Payment - Authorization Response Parameter](./api/nicepay-api-billing.md#recurring-payment---authorization-response-parameter).
- **Recurring Payment charges in KRW only, and the response `currency` is always `KRW`.** The manual listed `KRW`, `USD` and `CNY` as `currency` values. Send `amount` as a whole number of won, and convert other currencies before the call. See [Recurring Payment - Authorization Request Parameter](./api/nicepay-api-billing.md#recurring-payment---authorization-request-parameter).
- **A charge response `payMethod` is `card` or an easy pay value, including `tosspay`.** The manual listed `vbank`, `bank` and `cellphone`, and not `tosspay`. Accept `card`, `naverpay`, `kakaopay`, `samsungpay` and `tosspay`. See [Recurring Payment - Authorization Response Parameter](./api/nicepay-api-billing.md#recurring-payment---authorization-response-parameter).
- **A charge response has `status` `paid` or `failed` only, with `cancelledTid` always `null` and `cancelledAt` always `0`.** The manual listed `ready` and cancellation statuses and described cancellation data in this response. Read later cancellations from Transaction Status Inquiry. See [Recurring Payment - Authorization Response Parameter](./api/nicepay-api-billing.md#recurring-payment---authorization-response-parameter).
- **`orderId` must be unique across charges, Key-in payments and partial cancellations, but a declined charge releases it.** The manual said `orderId` is never reusable. Resend a declined charge with the same `orderId`. See [Recurring Payment - Authorization Request Parameter](./api/nicepay-api-billing.md#recurring-payment---authorization-request-parameter).
- **Delete Token returns `authDate` whether the deletion succeeded or failed.** The manual said `authDate` is returned only on success. Check `resultCode`, not the presence of `authDate`, to confirm a deletion. See [Delete Token(bid) Response Parameter](./api/nicepay-api-billing.md#delete-tokenbid-response-parameter).
- **Bid Status Inquiry (`POST /v1/subscribe/{bid}/status`) checks whether a Toss Pay token is still active.** Not documented before. Use it for `tosspayBill` tokens only (other `method` values fail with `U119`), and test it in Live because Sandbox does not support it. See [Bid Status Inquiry](./api/nicepay-api-billing.md#bid-status-inquiry).
- **Deleting an Easy Pay token needs `method`, and a Naver Pay or Toss Pay token also needs `reason`.** Not documented before. Send the token's `method` (`naverCardBill`, `naverPointBill`, `kakaoBill` or `tosspayBill`) and, except for `kakaoBill`, a non-blank `reason` (`U100` otherwise). See [Delete Token(bid) Request Parameter](./api/nicepay-api-billing.md#delete-tokenbid-request-parameter).
- **The charge request takes an optional `method` naming how the token was issued.** Not documented before. Send `naverCardBill`, `naverPointBill`, `kakaoBill` or `tosspayBill` for a token issued through that Easy Pay checkout, and leave it empty for a card token. See [Recurring Payment - Authorization Request Parameter](./api/nicepay-api-billing.md#recurring-payment---authorization-request-parameter).
- **The charge request takes an optional Boolean `useCardPoint`, `false` by default.** Not documented before. Send `true` to let a charge use card company points. See [Recurring Payment - Authorization Request Parameter](./api/nicepay-api-billing.md#recurring-payment---authorization-request-parameter).
- **The Create Token response has a `status` field: `issued` or `failed`.** Not documented before. Check `status` together with `resultCode` after each `regist` call. See [Create Token(bid) Response Parameter](./api/nicepay-api-billing.md#create-tokenbid-response-parameter).
- **Card token registration can fail with `F201` when the card network reports the card as already registered.** Not documented before. Treat `F201` (`status` `failed`, no `bid`) as a failed registration on `/v1/subscribe/regist` and Checkout `cardBill`. Easy Pay tokens do not return it. See [Create Token(bid) Response Parameter](./api/nicepay-api-billing.md#create-tokenbid-response-parameter).
- **The charge API's error codes are listed with what to do for each.** Not documented before. On `U112`, `U503` or `U506`, look the charge up by `orderId` before resending, and on validation codes such as `U100`, fix the request and resend. See [After a Recurring Payment charge](./api/nicepay-api-billing.md#after-a-recurring-payment-charge).
- **A declined charge gets no webhook and can be looked up by `tid` only.** Not documented before. Keep the `tid` from the decline response, because a lookup by `orderId` returns `U107`. See [After a Recurring Payment charge](./api/nicepay-api-billing.md#after-a-recurring-payment-charge).
- **Deleting a token that is already deleted or does not exist returns `U115`, not `0000`.** Not documented before. Treat `U115` from Delete Token as already deleted, not as a failure to retry. See [Delete Token(bid) Response Parameter](./api/nicepay-api-billing.md#delete-tokenbid-response-parameter).
- **Create Token, Delete Token and Bid Status Inquiry need a merchant ID for card payments without customer authentication, the one Key-in Payment uses.** Not documented before. Without it, Create Token fails with `U107` and the other two with `U313`. Ask NicePay to set it up before you build Recurring Payment. See [Recurring Payment - Create Token](./api/nicepay-api-billing.md#recurring-payment---create-token).
- **NicePay does not charge tokens on a schedule.** Not documented before. Run your own billing schedule and call `POST /v1/subscribe/{bid}/payments` each time a charge is due. See [Still not sure?](./INTEGRATION-PATHS.md#still-not-sure).
- **Recurring Payment in Sandbox is described.** Not documented before. Register card tokens only, encrypt `encData` with your Sandbox Secret key, and expect `cardCode` `04` whatever card you send. Sandbox does not validate the card number or check that the expiry date is in the future. See [Recurring Payment in Sandbox](./info/nicepay-info-sandbox.md#recurring-payment-in-sandbox).

#### Key-in Payment

- **Key-in Payment (`POST /v1/key-in/payments`) is documented.** Not documented before. It works in Live only and needs Key-in enablement on your account (`U313` or `A128` otherwise). Build `encData` on your server with AES-128 ECB, with exactly the fields your authentication type requires. See [Key-in Payment](./api/nicepay-api-keyin.md#key-in-payment).

#### Cancel

- **`orderId` in a cancel request identifies that cancel request, not the payment.** The manual described it as your unique order ID. For each partial cancellation, send a value never used before, not the payment's `orderId`, or the request fails with `U112`. See [Cancel Request parameter (with tid)](./api/nicepay-api-cancel.md#cancel-request-parameter-with-tid).
- **Cash receipt payments cannot be cancelled through the Cancel API.** The manual listed full and partial cancellation for them. Expect `U106` from either cancel endpoint, and do not send cash receipt cancellations there. See [Cancel / Refund period by Payment method](./api/nicepay-api-cancel.md#cancel--refund-period-by-payment-method).
- **`isNetCancel: true` cancels the full amount of a Checkout payment whose result your server did not receive.** Not documented before. Do not use it for Key-in or Recurring payments. Handle `U107`, `U120`, `U122`, and `2020` in Sandbox after 1 hour. See [Cancel Request parameter (with sessionId)](./api/nicepay-api-cancel.md#cancel-request-parameter-with-sessionid).
- **A partial cancellation cannot exceed what is left to cancel.** Not documented before. Check `cancelAmt` against the amount not yet cancelled (`U123`) and `taxFreeAmt` against the tax-free amount not yet cancelled (`U319`). See [Cancel Request parameter (with tid)](./api/nicepay-api-cancel.md#cancel-request-parameter-with-tid).
- **After a cancel request times out, look the payment up before you send it again.** Not documented before. Check `balanceAmt` and `cancels`, and resend a partial cancellation with a new `orderId`, because the same `orderId` fails with `U112` even when the first attempt failed. See [Timeout Information](./info/nicepay-info-firewall-timeout.md#timeout-information).

#### Transaction Status Inquiry

- **The orderId inquiry has no `orderDate` parameter.** The manual listed it as required. Stop sending it to `GET /v1/payments/find/{orderId}`. See [Transaction Status Inquiry (with orderId)](./api/nicepay-api-retrieve.md#transaction-status-inquiry-with-orderid).
- **`messageSource` was removed from two response tables.** The Check Authorization Amount and Interest-free installment information responses do not return it. Do not require it in those responses. See [Check Authorization Amount Response parameter](./api/nicepay-api-retrieve.md#check-authorization-amount-response-parameter).
- **The Card event API returns its interest-free array as `interestFree`.** The manual named it `interestFreet`. Read the array from `interestFree`. See [Card event API Interest-free installment information](./api/nicepay-api-retrieve.md#card-event-api-interest-free-installment-information-).
- **Check Authorization Amount is `POST /v1/check-amount/{tid}`.** The URI list and the Sandbox endpoint table said `GET`. Call it with `POST` and send `amount` in the JSON body. See [Check Authorization Amount Request parameter](./api/nicepay-api-retrieve.md#check-authorization-amount-request-parameter).
- **Interest-free installment information is `GET /v1/card/interest-free`.** The URI list gave `GET /v1/card/event`, which is the Card event API. Call `/v1/card/interest-free` for interest-free installment information. See [Interest-free installment information API](./api/nicepay-api-retrieve.md#interest-free-installment-information-api).
- **`vbank.vbankExpDate` can be `null`.** The manual marked it required. Handle a missing expiry date in inquiry and cancel responses and in webhooks. See [Virtual Account information](./api/nicepay-api-retrieve.md#virtual-account-information--).
- **`sessionId` is returned only for Checkout payments.** The manual marked it required in webhooks and left it out of inquiry and cancel responses. Do not require it. A webhook for a cancellation made with `tid` leaves it out too. See [Response parameter (Transaction Status Inquiry by tid, orderId, sessionId)](./api/nicepay-api-retrieve.md#response-parameter-transaction-status-inquiry-by-tid-orderid-sessionid).
- **`signature` is present on every successful inquiry and cancel response.** The manual marked it optional. Verify it on each response and do not cache it, because every inquiry returns a new `ediDate`. See [Response parameter (Transaction Status Inquiry by tid, orderId, sessionId)](./api/nicepay-api-retrieve.md#response-parameter-transaction-status-inquiry-by-tid-orderid-sessionid).
- **`signData` for the orderId inquiry is built from `orderId`.** The manual said to hash `tid` + `ediDate` + SecretKey. Build it as hex(sha256(`orderId` + `ediDate` + SecretKey)) for `GET /v1/payments/find/{orderId}`. See [Transaction Status Inquiry (with orderId)](./api/nicepay-api-retrieve.md#transaction-status-inquiry-with-orderid).
- **`payMethod` can also be `payco`, `ssgpay` or `tosspay`.** The manual listed only `card`, `vbank`, `bank`, `cellphone`, `naverpay`, `kakaopay` and `samsungpay`. Accept the three values in inquiry and cancel responses and in webhooks. See [Response parameter (Transaction Status Inquiry by tid, orderId, sessionId)](./api/nicepay-api-retrieve.md#response-parameter-transaction-status-inquiry-by-tid-orderid-sessionid).
- **`approveNo` is always `null` when you look up or cancel with `sessionId`.** The manual gave no such condition. Look the payment up by `tid` or `orderId` when you need the authorization number. See [Response parameter (Transaction Status Inquiry by tid, orderId, sessionId)](./api/nicepay-api-retrieve.md#response-parameter-transaction-status-inquiry-by-tid-orderid-sessionid).
- **For an issued, unpaid virtual account, `status` is `ready` and `paidAt` is when the account number was requested.** The manual described `ready` as ready and `paidAt` as `0` until payment. Decide payment by `status`, not `paidAt`. See [Response parameter (Transaction Status Inquiry by tid, orderId, sessionId)](./api/nicepay-api-retrieve.md#response-parameter-transaction-status-inquiry-by-tid-orderid-sessionid).
- **Check Authorization Amount returns `resultCode` `0000` even when the amounts differ.** The manual said only to cancel when they differ. Branch on `isValid`, which compares with the original approved amount. If it is `false`, cancel the full amount by `tid` without `cancelAmt` before delivering goods. See [Check Authorization Amount](./api/nicepay-api-retrieve.md#check-authorization-amount).
- **Transaction Status Inquiry takes `ediDate`, `signData` and `returnCharSet` as percent-encoded query parameters.** Not documented before. Send the `+` in the `ediDate` offset as `%2B`, or the `signData` check fails with `U312` in Sandbox and Live. See [Transaction Status Inquiry (with tid:Transaction ID)](./api/nicepay-api-retrieve.md#transaction-status-inquiry-with-tidtransaction-id).

#### Webhook

- **Webhook management uses `POST /v1/webhook`, `GET /v1/webhook` and `POST /v1/webhook/{method}/delete`.** The manual gave `/v1/webhook/regist`, `/v1/webhook/get` and `/v1/webhook/remove` in the URI list, and `GET` for delete. Call these paths and methods. See [URI LIST](./api/nicepay-api-uri-list.md#uri-list).
- **The webhook management endpoints take no `returnCharSet`.** The manual listed it on Create, Retrieve and Delete requests and in Create and Retrieve responses. Stop sending it. Retrieve takes no request parameters. See [Create webhook Request Parameter](./api/nicepay-api-webhook.md#create-webhook-request-parameter).
- **All four webhook management endpoints return every registered URL in a `urls` array.** The manual showed flat fields on Create, one `urls` object on Retrieve and nothing on Delete. Parse `urls` as an unordered array. A URL registered with `all` appears as four elements. See [Retrieve webhook Response Parameter](./api/nicepay-api-webhook.md#retrieve-webhook-response-parameter).
- **`method` also accepts `all` on Create, Update and Delete.** The manual's request tables listed only `card`, `bank`, `vbank` and `cellphone`. Send `all` to register, change or delete one URL for every payment method. See [Create webhook Request Parameter](./api/nicepay-api-webhook.md#create-webhook-request-parameter).
- **Answer each webhook with HTTP `200` and a body of exactly `OK` within 15 seconds.** The manual asked for a body containing `OK`, and its sample returned `500` for a non-`0000` `resultCode`. Store the event and answer `OK` first, even when a business check fails. See [Webhook dispatch flow](./api/nicepay-api-webhook.md#webhook-dispatch-flow).
- **Webhook failure emails go to your account's registered admin address.** The manual said NicePay emails `managerEmail`, which is only stored and echoed back. Make sure the admin address on your merchant account is monitored. See [Create webhook Request Parameter](./api/nicepay-api-webhook.md#create-webhook-request-parameter).
- **Webhook registration, lookup, update and delete work in Sandbox.** The manual listed them as not available in Sandbox. Register Sandbox URLs with your own Sandbox key, not the public test key, then register them again with your Live key. Sandbox cancellation events are not confirmed. See [Webhook](./api/nicepay-api-webhook.md#webhook).
- **NicePay sends webhooks only for successful events, so `status` is never `failed`.** The manual listed `failed` among webhook `status` values. Use Transaction Status Inquiry for declined payments and for payment methods with no registered URL. See [Delivery of webhook](./api/nicepay-api-webhook.md#delivery-of-webhook).
- **A webhook's charset follows the `returnCharSet` of the request that caused it.** The manual gave `utf-8` for every webhook. Decode the body with the charset in the `Content-Type` header. Checkout payment and virtual account deposit events are always `UTF-8`. See [Webhook event payload (sent by NicePay)](./api/nicepay-api-webhook.md#webhook-event-payload-sent-by-nicepay).
- **Verify each webhook's `signature` and confirm a deposit with Transaction Status Inquiry before shipping.** The manual said only to check `signature` and the amount. The signature does not cover `status` or `orderId`, and a deposit can be signed with another key pair's Secret key. See [Verifying a webhook](./api/nicepay-api-webhook.md#verifying-a-webhook).
- **`POST /v1/webhook/{method}/update` changes a registered webhook URL.** Not documented before. Send `url`, and optionally `managerEmail`, instead of deleting and re-creating the URL. See [Update a webhook](./api/nicepay-api-webhook.md#update-a-webhook-).
- **Each webhook management endpoint lists its error codes.** Not documented before. Handle `U100`, `U111`, `U133`, `U333` to `U338`, `U700` and `U701`. Retrieve returns `U111` with an empty `urls` array when no URL is registered. See [Create webhook Response Parameter](./api/nicepay-api-webhook.md#create-webhook-response-parameter).
- **Create and Update first send a test request that your URL must answer with `200` and `OK` within 5 seconds.** The manual said only that registration fails without `ok`. Deploy the endpoint first, handle `U336` to `U338`, and do not apply the test request to an order. See [Webhook](./api/nicepay-api-webhook.md#webhook).
- **The same webhook event can arrive more than once.** Not documented before. NicePay retries a failed delivery every minute, up to 10 attempts for an API-registered URL, and can resend an event you already answered. Store each event once under `tid` + `status` + `cancelledTid`. See [Webhook dispatch flow](./api/nicepay-api-webhook.md#webhook-dispatch-flow).
- **Key-in and Recurring Payment events go to the URL registered for `card`.** Not documented before. A Key-in event has the Key-in response fields with no `payMethod` or `cancelledTid`, and a Recurring event adds `bid`. Route events by `status` and `cancelledTid`. See [Delivery of webhook](./api/nicepay-api-webhook.md#delivery-of-webhook).
- **A cancellation webhook can arrive for a payment you never saw approved.** Not documented before. When NicePay's own processing fails after an approval, NicePay net-cancels the payment and sends a cancellation event. Handle a cancellation for an order that is not marked paid. See [Delivery of webhook](./api/nicepay-api-webhook.md#delivery-of-webhook).
- **A cancellation webhook keeps the original payment `amount`.** Not documented before. Match the event to the order by `tid`, and read `balanceAmt` and `cancels` for what was cancelled. See [Verifying a webhook](./api/nicepay-api-webhook.md#verifying-a-webhook).

#### Access token

- **The access token response has no `messageSource`.** The manual listed it in the response table. Remove any code that reads it. See [Access token API response (Body)](./api/nicepay-api-access-token.md#access-token-api-response-body).
- **The token expiry field is `expireAt`.** The manual's response table named it `expiredAt`. Read `expireAt` when you schedule token renewal. See [Access token API response (Body)](./api/nicepay-api-access-token.md#access-token-api-response-body).
- **`POST /v1/access-token` accepts only `Basic` credentials.** The manual said the `Authorization` header could also be `Bearer <token>`. Request every token with your Basic credentials, not with an existing Bearer token. See [Access token API request parameter](./api/nicepay-api-access-token.md#access-token-api-request-parameter).
- **`returnCharSet` on the access token request goes in the URL query string.** The manual did not say where to send it. If you send it, put it in the query string, for example `?returnCharSet=euc-kr`, not in the JSON body. See [Access token API request parameter](./api/nicepay-api-access-token.md#access-token-api-request-parameter).

#### Sandbox

- **There is no public Live key.** The manual published a Live Test key, and the old Quick Start called `api.nicepay.co.kr` with it. Test with the public Sandbox key on `sandbox-api.nicepay.co.kr`, and use your own Live merchant's keys in Live. See [Test key information](./info/nicepay-info-sandbox.md#test-key-information).
- **Card event and interest-free installment inquiries work in Sandbox and return fixed dummy data.** The manual listed both as unavailable in Sandbox. You can call `/v1/card/event` and `/v1/card/interest-free` there, but do not treat the data as real card company data. See [Sandbox limitations](./info/nicepay-info-sandbox.md#sandbox-limitations).
- **In Sandbox, a cancel request that contains `cancelAmt` fails, even for the full amount.** The Sandbox guide said to pass an amount for a partial cancellation. Leave `cancelAmt` out of Sandbox cancels, expect `U128` if you send it, and test partial cancellation in Live. See [Cancel](./info/nicepay-info-sandbox.md#cancel).
- **A Sandbox cancel response returns the payment's `orderId`, not the one in the cancel request.** Not documented before. Do not match a Sandbox cancel response by the `orderId` you sent in the cancel request. See [Cancel](./info/nicepay-info-sandbox.md#cancel).
- **Sandbox approvals return fixed card values and are always in KRW.** Not documented before. Card code is `04`, card number `123412******1234`, `cardQuota` `0` and approval number `000000`, whatever the request sends. Do not build tests that depend on these values or on `currency`. See [Sandbox limitations](./info/nicepay-info-sandbox.md#sandbox-limitations).

#### Amounts, dates, signatures and shared fields

- **Cancellation fields are `cancelledTid`, `cancelledAt` and `cancels[].cancelledAt`, with a double l.** The manual named them `canceledTid` and `canceledAt`. Read the double-l names in Transaction Status Inquiry, Cancel, Webhook and Recurring Payment responses. See [Response parameter (Transaction Status Inquiry by tid, orderId, sessionId)](./api/nicepay-api-retrieve.md#response-parameter-transaction-status-inquiry-by-tid-orderid-sessionid).
- **Payment `status` spells `cancelled` and `partialCancelled` with a double l and never returns `expired`.** The manual described `canceled` and listed `expired`. Match the double-l values exactly and remove any branch that waits for `expired`. See [Response parameter (Transaction Status Inquiry by tid, orderId, sessionId)](./api/nicepay-api-retrieve.md#response-parameter-transaction-status-inquiry-by-tid-orderid-sessionid).
- **`card.canPartCancel` and `card.isInterestFree` are JSON Booleans that can be `null`.** The manual typed `canPartCancel` as a String and marked `isInterestFree` as always present. Parse both as booleans and handle `null`. See [Card information](./api/nicepay-api-retrieve.md#card-information--).
- **`card.cardNum` shows the first 6 and last 4 digits, and `cardType` is up to 6 bytes.** The manual masked the third group (`53611234****1234`) and gave `cardType` 1 byte. Do not parse fixed mask positions, and handle `card` being `null` on non-card and failed payments. See [Card information](./api/nicepay-api-retrieve.md#card-information--).
- **Request `ediDate` is required whenever you send `signData`.** The manual marked it optional on some APIs, required on others, and called it a response creation time. Use identical `ediDate` text in the request and the `signData` hash, and write `signData` in lowercase hex. See [Dates in requests](./info/nicepay-info-general.md#dates-in-requests).
- **`bank.bankName` is a plain bank name with no special encoding.** The manual said it was EUC-KR encoded. Remove any EUC-KR decoding of `bankName` and read it in the charset of the response. See [Bank transfer information](./api/nicepay-api-retrieve.md#bank-transfer-information--).
- **Payment results, cancel and status inquiry responses, and webhooks use the `tid + amount + ediDate + SecretKey` signature, in lowercase hex.** The manual never gave the hex case. Check Authorization Amount signs `tid + ediDate + SecretKey`, card event and interest-free inquiries sign `ediDate + SecretKey`, and token responses have none. See [One thing all three share, and one thing that differs](./INTEGRATION-PATHS.md#one-thing-all-three-share-and-one-thing-that-differs).
- **NicePay never cancels a payment because your server timed out.** The manual said to send a cancel request after a read timeout. Look the payment up before keeping or cancelling it, and never resend a Key-in or Recurring charge with a new `orderId`. See [Timeout Information](./info/nicepay-info-firewall-timeout.md#timeout-information).
- **All four outbound firewall entries use `121.133.126.64/27`.** The manual wrote the same range as `121.133.126.85/27`, `121.133.126.84/27` and `121.133.126.83/27`. Check that your firewall allows the whole `/27` range and did not store those values as single hosts. See [Firewall Policy](./info/nicepay-info-firewall-timeout.md#firewall-policy).
- **Response dates are KST in `yyyy-MM-dd'T'HH:mm:ss.SSSZ`, with a `+0900` offset that has no colon.** The manual said only ISO 8601. Parse with a pattern that accepts `+0900`, check `paidAt`, `failedAt` and `cancelledAt` for the text `0` first, and hash `ediDate` exactly as received. See [Dates in responses](./info/nicepay-info-general.md#dates-in-responses).
- **Every amount is a whole number, and `currency` takes only `KRW`, `USD` or `CNY` in upper case.** The manual typed amounts as `Int` and listed the currencies without these rules. Send integers, because NicePay drops a fraction, and confirm the `USD` or `CNY` unit through this manual's issue tracker. See [Amounts and currencies](./info/nicepay-info-general.md#amounts-and-currencies).
- **NicePay computes `supplyAmt`, `goodsVat` and `serviceAmt` from `amount` and `taxFreeAmt`, with 10% VAT in every currency.** Not documented before. Key-in, Recurring Payment and Cancel ignore these three fields when you send them. Set the split with `taxFreeAmt` only, at or below `amount` (`U327` on Checkout, `U321` on Key-in and Recurring Payment). See [Tax breakdown](./info/nicepay-info-general.md#tax-breakdown).
- **The payment network, not NicePay's API, decides whether a foreign currency or an overseas-issued card is accepted.** Not documented before. Handle `A145`, `A146`, `A248`, `3051` and `3053`, and expect a `currency` other than `KRW` only from card and easy-pay payments. Sandbox always returns `KRW`. See [Accepting overseas customers](./info/nicepay-info-general.md#accepting-overseas-customers).

#### Response codes

- **`2032` means only that the cancellation amount exceeds the cancelable amount.** The manual also listed it as an over-length order number. Handle `2032` as a cancel error only. See [API response code](./code/nicepay-code.md#api-response-code).
- **`F101` is a failure: PKCS7 signature or encrypted-message verification failed (Recurring Payment, Key-in).** The manual said "Billing information has been deleted", which reads like a success. Treat `F101` as a failure, never as a successful token deletion. See [API response code](./code/nicepay-code.md#api-response-code).
- **`2011`, `2012` and `C002` each have two meanings, and the table now labels the context of each.** The manual listed both meanings with no context. Read these codes by the API that returned them, for example `2011` on a cancel is an amount mismatch. See [API response code](./code/nicepay-code.md#api-response-code).
- **`U324` means the `sessionId` was already used.** The manual said "Session ID already issued". Create every checkout session with a new `sessionId`, even when the earlier session expired or failed. See [API response code](./code/nicepay-code.md#api-response-code).
- **`U332` applies only to the `cardAndEasyPay` method.** The manual said no Easy Pay method accepts `cardCode` and `cardQuota`. You can send them with the other Easy Pay methods, within the limits of `U136`, `U138` and `U141`. See [API response code](./code/nicepay-code.md#api-response-code).
- **`2020` means the time window for a net cancel has passed.** The manual described it as the time limit for canceling virtual transactions. Do not route `2020` to virtual account handling. See [API response code](./code/nicepay-code.md#api-response-code).
- **`3062` means a credit card approval number error.** The manual translated it as a card number error, the same as `3011`. Update any message or handling you mapped to `3062`. See [API response code](./code/nicepay-code.md#api-response-code).
- **The `0000` row shows the `resultMsg` that the API actually returns.** The manual showed a different Korean message. Never decide success from the `resultMsg` text. See [API response code](./code/nicepay-code.md#api-response-code).
- **`P045`, `P047` and `P049` are listed, and a second `returnUrl` callback for a successful session can carry them.** Not documented before. On these codes, keep an order that is already paid and look the payment up with Transaction Status Inquiry instead of failing it. See [Verifying the payment result](./api/nicepay-api-payment-window-url.md#verifying-the-payment-result).
- **`U701` means that the webhook could not be logged, but the transaction succeeded.** Not documented before. Treat `U701` as a successful transaction, not as a failure. See [API response code](./code/nicepay-code.md#api-response-code).
- **`9999` is listed as a temporary NicePay error.** Not documented before. Treat it as a failed request. See [API response code](./code/nicepay-code.md#api-response-code).
- **Key-in has its own codes: `U340` when NicePay cannot decrypt `encData`, and `U341` when `encData` does not match your authentication type.** Not documented before. Handle them in your Key-in error path. See [API response code](./code/nicepay-code.md#api-response-code).
- **The table adds `U133` to `U154`, `U326` to `U331`, `U339`, `U343` to `U345`, `U510` and `2045`.** Not documented before. They cover request format, installment, Easy Pay, `vbankExpDate`, amount, tax, escrow, `bid`, token deletion and partial cancel checks. Add them to your error handling. See [API response code](./code/nicepay-code.md#api-response-code).
- **`4126`, `4127`, `A303`, `M001` and `M002` mean your account is not set up for the partner institution behind a bank transfer, virtual account or mobile carrier payment.** Not documented before. Get the account set up instead of changing the request. See [API response code](./code/nicepay-code.md#api-response-code).
- **Card code `46` is Toss Money.** Not documented before. Map it if you display or store card company names. See [Card code](./code/nicepay-code.md#card-code).

#### Reconciliation (Beta)

- **The field is `originalTid` in Transaction Search and Settlement responses.** The manual spelled it `originlTid`. Read `originalTid`. See [Transaction Search API Response parameter](./api/nicepay-api-reconciliation.md#transaction-search-api-response-parameter--).
- **Settlement responses have no `sendDate`.** The manual listed it as the scheduled settlement send date. Use `paidOutDate` for the scheduled settlement date. See [Settlement API Response parameter](./api/nicepay-api-reconciliation.md#settlement-api-response-parameter).
- **Settlement `cardAcquiringStatus` is a Boolean, `true` once the acquirer has recorded an acquiring date.** The manual typed it as a String holding payment status values. Parse it as a boolean. See [Settlement API Response parameter](./api/nicepay-api-reconciliation.md#settlement-api-response-parameter).
- **Settlement `net` is a single object with `krw` and `usd` amounts.** The manual typed it as an Array. Parse `net` as an object. See [Settlement API Response parameter](./api/nicepay-api-reconciliation.md#settlement-api-response-parameter).
- **Settlement `startingSequence` is a String, as in Transaction Search.** The manual typed it as an Integer. Send it as a string. See [Settlement API Request parameter](./api/nicepay-api-reconciliation.md#settlement-api-request-parameter).
- **Transaction Search and Settlement use `GET`.** The URI list gave `POST` for `/v1/transactions` and `/v1/settlements`. Call both endpoints with `GET`. See [URI LIST](./api/nicepay-api-uri-list.md#uri-list).
- **Settlement `type` is optional and has no effect.** The manual marked it required. You can leave `type` out of Settlement requests. See [Settlement API Request parameter](./api/nicepay-api-reconciliation.md#settlement-api-request-parameter).
- **`transactionStatus` can be `paid`, `cancelled`, `partialCancelled`, `vbankCreate` or `vbankCancelled`.** The manual listed only `paid`, `canceled` and `partialCancelled`. Match `cancelled` with a double l and handle the two virtual account values in Transaction Search and Settlement. See [Transaction Search API Response parameter](./api/nicepay-api-reconciliation.md#transaction-search-api-response-parameter--).
- **`pagination.count` is the total number of matching records for the date, not the size of the current page.** The manual said it counted the objects in the response. Page with `hasMore` and `nextSequence` instead. See [Transaction Search API Response parameter](./api/nicepay-api-reconciliation.md#transaction-search-api-response-parameter--).
